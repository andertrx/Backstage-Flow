# 40.5 — Publicação das Edge Functions pela CLI (12/11/2026)

> O que foi auditado, o que estava atrasado e como publicar agora sem colar arquivo à mão.

## 1. Por que esta fase existe

Até 11/11/2026 a única forma de publicar uma Edge Function era **empacotar o código num arquivo
único e colar à mão** pelo painel do Supabase. Isso travava as publicações: as funções grandes
(`sync`, `ad-accounts`) ficaram meses com o código do GitHub mais novo do que o que estava no ar,
e a pendência "publicar a função `mcp`" (T5.22, T5.32, T5.33) se acumulou.

Com o ambiente local preparado (Node, CLI do Supabase autenticada e a pasta linkada ao projeto),
a publicação virou **um comando** — o mesmo que o workflow `.github/workflows/publicar-funcao.yml`
já usava.

## 2. Auditoria: o que estava no ar contra o código local

Conferido em 12/11/2026, comparando a data da última alteração local (git) com a versão/ data
publicada (`supabase functions list --output json`):

| Função | Publicada em | Última mudança local | Situação |
|---|---|---|---|
| `mcp` | 11/11 00:11 (v8) | 11/11 11:04 (subtarefas) e 11/11 06:09 (responsável obrigatório) | **atrasada** — faltava responsável obrigatório e subtarefas |
| `ad-accounts` | 28/10 22:57 (v15) | 28/10 23:01 (Criador de Anúncios, 42.1) | **atrasada em 1 commit** — faltava a ação `refresh_assets` ("Atualizar do Meta" no Criador de Anúncios) |
| `sync` | 08/11 16:27 (v16) | 26/09 16:31 | **em dia** — a regra do saldo (28/09) e o ID do criativo já estão no ar |

O aviso antigo da documentação ("sync e ad-accounts estão mais novas no GitHub") **não vale mais
para o `sync`**: ele foi republicado em 08/11/2026.

O banco também está em dia: **131 migrations aplicadas, nenhuma pendente** (`supabase migration
list --remote`).

## 3. O que mudou no código

- `supabase/functions/mcp/tools.ts`: `MCP_VERSION` foi de **1.5.0 para 1.6.0**, para que a versão
  que responde em `backstage_status` e no guia (`backstage://guia`) identifique o servidor novo
  (responsável obrigatório + subtarefas na repetição).
- `supabase/functions/mcp/mcp_test.ts`: o teste que fixa a versão foi atualizado junto.

Nada mais mudou: o resto do código já estava escrito e testado (T5.32/T5.33).

## 4. Como publicar (novo caminho)

A CLI está autenticada na máquina do Ander (`supabase.cmd login`, feito em 12/11/2026) e a pasta
está linkada ao projeto `dkatllzkmlzpginuzvis`.

```bash
# mcp: precisa de --no-verify-jwt (o login é conferido dentro da função)
supabase.cmd functions deploy mcp --remote=dkatllzkmlzpginuzvis --use-api --yes --no-verify-jwt

# ad-accounts: verify_jwt continua ligado (true)
supabase.cmd functions deploy ad-accounts --remote=dkatllzkmlzpginuzvis --use-api --yes
```

- `--use-api`: empacota no servidor, sem Docker, e leva junto o `packages/shared` (as funções
  importam arquivos de fora da própria pasta).
- **`verify_jwt`**: cada função tem o seu. Só o `mcp` usa `false` (o OAuth do Supabase passa por
  ela). `sync`, `track`, `capi-sender`, `whatsapp-webhook` e `client-report-*` também usam `false`
  porque conferem o acesso por conta própria. Conferir antes: `supabase.cmd functions list --output json`.
- Conferir depois: `supabase.cmd functions list` (versão e data) e
  `supabase.cmd functions download <nome> --remote=dkatllzkmlzpginuzvis --workdir <pasta>`
  para comparar com o arquivo local.

O caminho antigo (empacotar e colar à mão) continua valendo se a API recusar uma função grande.

## 5. Alternativa pelo GitHub

O workflow `.github/workflows/publicar-funcao.yml` (botão **Actions → Publicar função do Supabase**)
faz o mesmo, mas precisa do segredo `SUPABASE_ACCESS_TOKEN` em *Settings → Secrets and variables →
Actions*. O token do Ander serve; cole **só lá**, nunca no chat. Com o segredo, a publicação passa a
ser um botão na tela do GitHub, sem depender de terminal.
